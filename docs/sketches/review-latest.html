1. The new contract, against the invariants

"Any function declared async is lowered to a coroutine. Transformation happens on build artifacts, never on the user's files. No .async.cpp naming (AUTOMOC-like). LSP and completion are mandatory." The user chose an LSP proxy with unchanged syntax.

2. Build flow: before and after

Before (today): suffix-driven custom commands

src/main.async.cpp
only this suffix is transpiled; headers cannot contain async ↓ add_custom_command (asynctp) build/…/asynctp_generated/app/main.cpp ↓ c++ -c object file compile_commands.json lists the generated file clangd has no entry for the user's file hand-written Task<T> in headers

After: compiler launcher (AUTOMOC-like)

src/main.cpp · src/jobs/jobs.hpp · src/jobs/jobs.cpp
plain names; async anywhere, headers included ↓ CMake: CXX_COMPILER_LAUNCHER = asynctp-cc --root … --shadow … -- asynctp-cc T-0014
scan deps, mirror and lower into the shadow tree, rewrite -I, run the real compiler, rewrite the depfile ↓ c++ -c <shadow copy> object file; diagnostics point at the original file (single #line, line-preserving lowering, T-0012) compile_commands.json = original file + plain flags sources never written header edits trigger rebuilds

Rejected alternative: custom commands without the suffix. The compile DB would still list generated files, a configure-time scan goes stale, and headers stay invisible (T-0014 Notes).

3. The asynctp-cc launcher path (one compile)

1. classify

sources by extension; value-taking options table; link, -E and non-C++ invocations pass through. Unsupported modes (PCH, modules, MSVC) are noted.

2. scan

user's flags minus -c -o -MD -MF -MT, plus -MM -MF tmp, giving the non-system deps. ~56 ms vs ~430 ms compile

3. decide

classified markers (T-0004) in the TU or in deps under --root?
none: exec unchanged; nothing written.

4. mirror

marker files: strict lower_file; others: BOM, then #line 1 "orig", then bytes. Atomic write-if-changed.

5. compile and fix up

source → shadow path; shadow twin before every -I/-iquote; trailing -iquote <tu dir>; run; depfile shadow→original; bypass post-check. 
CMake invokes (verified):  asynctp-cc --root /proj --shadow /proj/build/asynctp-shadow -- /usr/bin/c++ -I/proj/src -std=gnu++20 -MD -MT obj -MF obj.d -o obj -c /proj/src/main.cpp
asynctp-cc runs:           /usr/bin/c++ -I /proj/build/asynctp-shadow/proj/src -I/proj/src -std=gnu++20 -MD -MT obj -MF obj.d -o obj \
                             -c /proj/build/asynctp-shadow/proj/src/main.cpp -iquote /proj/src
depfile after rewrite:     obj: /proj/src/main.cpp /proj/src/jobs/jobs.hpp /proj/src/jobs/detail.hpp …

prototype built, ran, rebuilt on original-header edit, no-op rebuild compiled nothing plain std::async TU broke the prototype build until T-0004 empty prior-launcher list element: Error 126 (T-0015 pitfall)

4. Header shadow scheme

Source tree (read-only to us)

/proj/src/main.cpp          #include "jobs/jobs.hpp"
/proj/src/jobs/jobs.hpp     #include "detail.hpp"
                            async int download(int n);
/proj/src/jobs/detail.hpp   constexpr int K = 100;

Shadow tree: <build>/asynctp-shadow/<absolute path>

…/proj/src/main.cpp        lowered    (prelude, #line 1 "/proj/src/main.cpp", …)
…/proj/src/jobs/jobs.hpp   lowered    ::asyncrt::Task<int> download(int n);
…/proj/src/jobs/detail.hpp mirrored   #line 1 "/proj/src/jobs/detail.hpp" + bytes
RuleWhy (evidence)
Mirror every non-system header the TU reaches, not just async onesverified GCC resolves "x.hpp" against the physical file's dir. Shadowing only jobs.hpp gave fatal error: detail.hpp: No such file or directory.
Shadow twin inserted before each project -I/-iquoteverified #include <jobs/jobs.hpp> finds the lowered copy first.
Lower only under --root; mirror outside roots verbatimthird-party headers that use async as an identifier are never rewritten
Depfile shadow paths rewritten to originalsverified otherwise editing the original header never triggers a rebuild
BOM stays the first bytesverified a BOM after #line gives '﻿int' does not name a type
Trailing -iquote <tu dir>keeps __has_include("x.h") right for headers tested but not included

Failure modes (all loud): absolute #include "/proj/src/jobs/jobs.hpp": bypass post-check error unity builds (absolute includes): same post-check #include_next in a mirrored header may reach the original PCH / modules / MSVC: explicit "unsupported" error when markers are present Ninja: compile_commands behaviour not verified here
